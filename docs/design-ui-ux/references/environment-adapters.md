# Portable execution adapters

## Capability discovery

Inspect the actual workspace, available tools, repository instructions, assets, package manifests, and platform conventions before selecting a workflow. Do not assume a particular provider, operating system, framework, browser, paid plugin, or design editor. Use relative paths from this skill's directory for its bundled resources; do not embed installation paths into generated deliverables.

The core method requires only reading and producing structured instructions or an artifact. File access, code execution, browser rendering, design-editor APIs, network access, and Python are optional capability layers. Use the best authorized layer available; follow host tool and permission rules. This skill does not grant permission to publish, spend, message others, or modify unrelated systems.

## Existing source code

Read relevant local instructions and inspect existing routes, components, styles/tokens, dependencies, content, and tests. Reuse the stack, router, accessibility primitives, icon library, and design conventions where sound. Make scoped changes; preserve unrelated modifications and backend contracts. Do not install a new UI framework to change spacing.

Use intrinsic layout and semantic controls. Centralize repeated values in existing tokens or a small appropriate layer. Name components by purpose and state. Inspect production build behavior where relevant; development-only success may hide broken assets or routes. Do not claim a service is connected merely because a click changes local state.

## New implementation with runtime

Use the requested platform/stack. If absent, choose the simplest suitable implementation supported by the environment. A static content page can be dependency-light; an application should follow the available project setup. Define the task, content, layout, tokens, states, and responsive behavior before generating many components.

Use local/authorized assets and fallback fonts. Avoid runtime dependence on paid assets or a transient network URL unless required and reliable. Do not fetch/install unnecessary packages. Make a navigable, functioning slice first; extend to requested coverage. If no backend is available, mark simulated operations or local-only persistence explicitly and avoid fake transactional success.

## Design editor

Use the available design API or established editor workflow. Create semantic frames and components, consistent variants, explicit spacing and constraints, text styles, color roles, and meaningful layer names. Use auto layout/constraints as soon as they improve adaptability; freeform exploration is optional and should not leave brittle absolute geometry in the final design.

Use native/current kit dimensions only when verified. Preserve reusable components instead of indiscriminately detaching them. Match prototype transitions to actual states, wire forward and back paths, and preserve matching layer identities when animating. Inspect rendered frames at intended size and a small-screen/text-stress variant. Do not report interaction testing if only static frames exist.

## Screenshot or image only

Inspect the image itself. Estimate layout, grouping, typography, contrast risks, and behavior cues. Distinguish measured screenshot pixels from unknown CSS/native units. Do not invent hidden screens, code, backend behavior, or user research. If tasked with improving it, produce an annotated change specification or a rebuilt design in an available medium, with assumptions about interaction identified. If exact editing requires a missing source, complete the useful visual analysis and then name the needed input.

## No execution or visual rendering

Produce an implementation-ready design specification: working brief; screen/flow map; content and component anatomy; token roles and values; layout constraints; state/behavior matrix; responsive transformations; accessibility requirements; verification scenarios. Include concrete examples rather than adjectives alone. If code output is possible, provide source with a clear “not rendered/tested” limit. Do not claim pixel-perfect or cross-device validation without a renderer.

## Limited file/context access

Keep SKILL.md as the operating kernel. For a file-capable host, resolve and load the required reference modules explicitly. For a context-only host, load the relevant bundled text alongside the kernel; no original transcript or external tutorial is needed. If only the kernel is available, follow its abbreviated workflow and checks, and state that detailed references were unavailable rather than pretending to have applied them.

## Verification tools

Use an available browser, renderer, emulator, screenshot tool, or editor preview within the host's authorized workflow. Inspect at least representative states and sizes. Use existing test tools for behavior where appropriate. When using a static contrast calculator, provide actual resolved solid colors; use a proper renderer for alpha, gradients, and filters. The bundled script has no third-party Python dependencies and is optional.

Publish/deploy only when the user request or established workflow authorizes it, and use the host's required hosting mechanism. Creating the design and deploying a live service are separate capabilities. If deployment is unavailable, deliver the runnable artifact or specification and clearly state that limit.
